ACT 1

The Problem — The Fragmented Student Crisis

00:00 – 02:00
📺 Slide 1: Fragmented browser with 15 open tabs (Classroom, GitHub, Gmail, Codeforces, Calendar)
“Good morning, respected supervisor and members of the panel. Today, we are presenting our Capstone project: Student OS, codenamed Kairo.

To understand why Kairo is necessary, consider the daily workflow of an engineering student. On any given Tuesday, an engineering student has assignments due on Google Classroom, upcoming standups on Google Calendar, pull requests and merge conflicts on GitHub, competitive rounds on Codeforces, and time-sensitive internship offers buried on Gmail.

The core dilemma is not a lack of productivity tools—it is acute cognitive fragmentation. Students burn 20 to 30 minutes every morning tab-switching across 5 to 7 platforms, manually piecing together what is urgent and what can wait.

Existing solutions fail fundamentally: traditional to-do apps like Notion require manual data entry (if a student forgets to type in an assignment, it does not exist), while generic AI chatbots lack live execution context into the student's actual external accounts.

We asked ourselves: Can we engineer an autonomous, context-aware operating system that gathers all real-time academic and technical signals with zero manual data entry, intelligently prioritizes them, and builds a realistic, wellbeing-aware day plan? That is Kairo.”
ACT 2

The Solution Paradigm (Kairos)

02:00 – 04:00
📺 Slide 2: Philosophy & Core 4 Architectural Pillars
“The project is named Kairo, derived from the classical Greek concept of Kairos (καιρός)—which represents not chronological clock time, but the opportune, critical moment for action.

Kairo is engineered around four core innovations:
1. Zero Manual Data Entry via MCP: Utilizing Anthropic's Model Context Protocol, Kairo connects directly to platforms via sandboxed background subprocesses over stdio.
2. Context-Aware Multi-Strategy Ranking: We do not sort by deadline alone. Kairo pairs an interpretable rule-based engine with an empirical Closed-Form Ridge Regression Ranker that modulates priorities based on real-world context (such as reducing competitive coding prior to examinations).
3. Wellbeing-Aware Pacing & Daily Scheduling: Unlike naive calendars that overload students with 16-hour impossible schedules, Kairo uses a bin-packing scheduling algorithm with honest overflow and mandatory breaks.
4. Client-Agnostic Dynamic Security Vault: We decoupled all personal credentials from server .env files into an encrypted multi-tenant vault using Fernet AES-128-CBC and PBKDF2-HMAC-SHA256, allowing students to securely manage all accounts through the web browser from any computer.”

“Let us examine the backend engineering in detail. The backend is implemented in Python 3.11 with FastAPI.

1. Model Context Protocol (MCP) Orchestration: Rather than writing monolithic API scripts, each platform runs as an independent MCP stdio subprocess (GitHub, Gmail, Calendar, Codeforces, Classroom). When /briefing is called, our orchestrator launches them concurrently, collects tools, and extracts clean, unified ActionItem models.

2. The Ranking Problem & Pluggable Architecture: A naive deadline sort fails because an urgent scholarship email with no explicit deadline is buried, while an exam 4 days away is ignored until it is too late. We engineered two complementary rankers:

Strategy A: The Rule-Based Context Engine computes a composite score: $$\text{Score} = W_{\text{kind}} + \text{Boost}_{\text{due}} + W_{\text{category}} + \Delta_{\text{context}}$$ Where Exams are weighted at 6.0, Deadlines at 5.0, down to Passive Events at 1.0. Crucially, if the system detects an exam within 5 days ($\text{exam\_week} = \text{True}$), competitive practice receives a -4.0 dampening penalty to keep students focused on graded academic work.

Strategy B: The Machine Learning Ridge Ranker transforms items into a 30-dimensional feature vector across 6 orthogonal spaces (kinds, sources, categories, due buckets, context interactions) and trains a closed-form Ridge Regression ($\lambda = 1.0$): $$\mathbf{w}^* = (\mathbf{X}^T \mathbf{X} + \lambda \mathbf{I})^{-1} \mathbf{X}^T \mathbf{y}$$ This trains in 4 milliseconds without GPU dependencies, completely eliminating train-serve skew.

3. Dynamic Security Vault: Multi-tenant credentials are encrypted at rest with Fernet AES-128-CBC. Subprocesses receive decrypted tokens strictly in ephemeral RAM per execution, eliminating token leaks.”

ACT 7

Supervisor Viva Defense & Technical FAQs

14:00+

❓ Q1: Why use Ridge Regression instead of a Deep Neural Network or XGBoost?

Defense: “Three reasons: (1) Mathematical Explainability: In an academic viva, neural networks are black boxes. In Ridge regression, every weight $w_i$ is an interpretable coefficient (e.g. $\text{kind\_exam} = +1.8$). (2) Zero Latency: Closed-form $\mathbf{w}^* = (\mathbf{X}^T\mathbf{X} + \lambda\mathbf{I})^{-1}\mathbf{X}^T\mathbf{y}$ computes in 4ms with zero GPU/TensorFlow bloat. (3) Generalization: On tabular academic features, deep networks overfit easily. Ridge regression with L2 regularization ($\lambda = 1.0$) prevents co-linearity, proven by our 0.993 LOSO nDCG@5.”

❓ Q2: How do you handle rate limits and network errors from external APIs?

Defense: “We implement a 3-tier Graceful Degradation model: (1) Process Isolation: Every platform runs in a sandboxed subprocess; if GitHub times out, asyncio.wait_for aborts it without blocking Gmail or Codeforces. (2) TTL Cache Layer: Items are cached per-user (student_os:v2:items:user_<id>) to avoid redundant API hits. (3) Degraded Fallback: If an API fails with 403, Kairo surfaces a clear status banner or falls back to offline cached state so the briefing never crashes.”

❓ Q3: How is student privacy guaranteed in a shared multi-tenant environment?

Defense: “We employ defense-in-depth: user passwords use PBKDF2-HMAC-SHA256 with 100k rounds; sessions use signed JWTs with 7-day expiration; external tokens are encrypted at rest via Fernet AES-128-CBC; and decrypted credentials exist strictly in transient RAM within the short-lived subprocess spawned for that authenticated user's turn.”

❓ Q4: Why use nDCG instead of Accuracy or F1-Score?

Defense: “Accuracy and F1-score evaluate classification (whether an item is important or not). But in a daily briefing, ranking order matters—an urgent exam must appear at position #1, not position #5. Normalized Discounted Cumulative Gain (nDCG) logarithmically discounts relevance lower down the list. An nDCG@5 score of 0.993 proves that critical tasks appear at the top where the student actually looks.”
